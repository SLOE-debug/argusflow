# ArgusFlow 协作规范

## 兼容性

- 除非用户明确要求，否则不要主动添加任何兼容性代码。
- 发现新旧逻辑或字段契约不一致时，默认直接对齐当前目标方案；不要补兼容分支、兼容映射、回退逻辑或双写逻辑。

## 文件体积与职责拆分

- 写新功能前先判断职责边界，不要把实现持续堆进单个文件。
- 单个文件超过 500 行时，必须停下并评估拆分，不得明知超线仍持续追加实现。
- 一个文件承担多类职责时必须拆分；入口文件优先只保留编排职责。
- 转换、映射、构造、解析、校验、持久化、渲染和业务细节应下沉到独立文件。
- 在实现过程中控制文件体积，发现职责外溢立即整理结构，不要等收尾再拆分。
- 不得为了减少补丁次数，把应独立的 helper、模型、转换逻辑或工具逻辑临时塞进同一文件。

## 开发验证

- 功能开发完成后，除非用户明确要求，否则不要主动使用浏览器技能或浏览器自动化工具进行测试、验收或演示。
- 浏览器端验证默认由用户执行；不要擅自打开页面、点击操作、截图检查或执行浏览器回归。
- 查资料、阅读文档、检索信息不受上述限制。

## 提交更改

当用户说“提交更改”或类似指令时：

1. 运行 `git status` 查看所有文件的修改状态。
2. 识别不应上传的文件类型，如 Godot `.uid`、构建产物和 IDE 配置；缺少忽略规则时先写入 `.gitignore`。
3. 使用 `git add .` 暂存全部改动，由 `.gitignore` 排除忽略项。
4. 根据文件名、路径、修改状态或任务上下文了解变更；信息不足时再按需查看统计或关键 diff，不强制逐个文件检查。
5. 提交 working tree 中所有未被忽略的改动，不仅限于当前对话修改的文件。

## 提交信息

- Git 提交信息必须使用中文，不写英文摘要或英文要点。
- 优先采用“首行摘要 + 空行 + 变更要点列表”；可保留 `feat:`、`fix:`、`refactor:` 等前缀，冒号后的摘要必须为中文。
- 正文按已确认的变更概括，每行聚焦一个主要改动，避免编造未确认细节。
- 包含协作者信息时保留 `Co-Authored-By:` 尾注，不得擅自删除。

## 本地文件操作

- 读取、搜索和查找本地文件时，优先使用 FastCtx 的 `inspect_local_file`、`grep` 和 `glob`。
- URI 形式的本地引用应转换为普通绝对文件系统路径，直接交给 FastCtx。
- 仅读取任务需要的内容；多个文本文件通过 `inspect_local_file` 的 `files` 参数批量读取。
- 返回 `Partial` 时，使用工具给出的精确续读参数继续，直到所需内容读取完整。
- 机械式批量替换使用 FastCtx `replace`，保留文件编码和换行并检测并发修改。
- 生成内容、语义改写或小范围编辑使用 `apply_patch`。
