# ArgusFlow 通用编码与架构规范

适用于所有前端、后端及跨端模块。前端和后端规范都必须在这些共同约束下执行。

## 核心原则

- 强类型优先。类型必须表达真实的领域约束、输入输出关系和状态边界，不以散落字符串、弱类型容器或隐式约定代替模型。
- 高内聚、低耦合是强制架构约束；模块、文件或组件职责边界不清时，必须先拆分再继续实现。
- 入口文件只负责注册、装配和编排，不承载转换、映射、构造、解析、校验、持久化、渲染或具体业务细节。
- 对外只暴露稳定、最小且尽可能只读的契约；内部可变状态和实现细节不得被调用方任意修改。
- 不为了追求“通用”提前制造空抽象；泛型、Trait、接口和注册表必须表达真实复用关系或依赖边界。

## 适度抽象与模块接入

- 无论前端还是后端，都必须以适度抽象、高可用、高内聚、低耦合的方式开发；各模块各司其职，通过明确的契约协作。
- 抽象必须对应当前真实的职责、变化点或外部依赖边界。可以为真实的平台隔离建立单实现接口，但不得只为假想的未来需求堆叠接口、基类、泛型、注册表或转发层。
- 同一职责的规则、状态和生命周期集中管理；不同职责通过组合协作，不把跨模块业务塞进底层工具，也不让一个模块成为全能服务。
- 先明确模块负责什么、不负责什么、输入输出、错误语义和生命周期，再实现内部细节。调用方只依赖最小稳定契约，不读取或修改其他模块内部状态。
- 契约应由拥有该语义的模块或独立的契约模块维护；不得为了共享而把所有接口和模型塞进 core，不得复制同一协议结构。
- 新模块应通过实现已有能力契约并在装配边界接入；若新能力确实需要扩展契约，应显式调整类型与调用方，不得散落实现名称判断、字符串分发或平台分支。
- 底层能力不得反向依赖上层业务。具体实现的选择、依赖注入与跨模块连接放在装配层；入口只编排，具体适配逻辑进入独立适配模块。
- 抽象是否合适，以调用方是否无需了解实现细节、职责是否清晰、变更是否局部化为依据，不以层数、接口数量或文件数量为依据。

## 高可用与故障边界

- 高可用必须落实为可预期的失败行为和可恢复的状态，按实际运行场景设计；不得为此提前引入集群、分布式框架或无需求的基础设施。
- 对外部 I/O、长任务和异步协作明确超时、取消、资源释放与错误传播语义；一个模块失败不应无边界地拖垮无关功能。
- 错误必须携带足够的类型和上下文供调用方处理，不得吞错、伪装成功或无限等待。状态转换应保证失败或取消后仍满足不变量。
- 重试只用于明确可重试且满足幂等或去重约束的操作，并设置次数或时间上限；不得自动重放有副作用的操作。
- 有持续事件流、后台任务或队列时，应按实际负载设置并发、容量或背压边界，避免资源无限增长。
- 为关键执行路径提供必要的状态和诊断信息，并验证关键失败、取消与资源清理路径；避免记录敏感数据。
- 故障处理不等于兼容旧协议，不得借“高可用”新增未经要求的兼容映射、静默回退或双写。

## 注释

- 除了名称足够直白、无需额外上下文就能准确理解用途的变量之外，变量声明都应补充注释。
- 即使变量名称表面可读，只要名称较长、语义拗口、依赖业务上下文、单位或取值范围不明确，或者可能产生二义性，也必须添加注释。
- TypeScript/JavaScript 优先使用 `/** ... */` 风格的详细注释；Rust 使用对应的文档注释 `///`、`//!`，局部实现细节可使用 `//`。
- 对公开类型、接口、函数、方法、字段、常量和模块添加文档注释，说明其用途、关键约束、输入输出以及必要的副作用；不要只把标识符名称换一种说法。
- 对复杂分支、状态转换、算法意图、边界条件和不直观的实现选择添加解释性注释，重点说明“为什么”，而非逐行复述“做了什么”。
- 简单循环索引、明显的布尔判断结果、惯用回调参数等一眼可懂的局部变量可以不注释，避免制造噪声。
- 注释必须与当前实现保持一致；修改代码时同步更新相关注释，不保留失效、猜测性或误导性描述。

## 目录与公共导出

- 跨目录引用优先通过对应目录的 `index.ts` 或 Rust 模块公开导出；模块内部实现才直接引用同一职责目录的具体文件。
- 目录迁移应通过 `scripts/refactor-layout.mjs` 或 `scripts/refactor-rust-layout.py` 的显式映射执行，并保持脚本可重复运行且不改变协议和算法语义。
