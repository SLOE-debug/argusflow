我看的是你 GitHub 上当前的 `SLOE-debug/argusflow`，重点把最近两个 AQL commit、`argusflow-query`、UIA/CDP compiler、ActionRouter，以及现在右侧的 `AqlEditor` 都过了一遍。最近两次正好就是 `2540d96`「实现 AQL 统一 UI 查询语言」和 `5890e10`「完善 Action 节点与 AQL 编辑器」。

整体方向其实很好，尤其是「AQL 不是 CSS subset」「语义查询 → planner → UIA/CDP/Vision」这条路线值得继续。现在真正限制它上限的，不是语法功能少，而是 **语言层、编辑器层、查询规划层、产品展示层还没有彻底解耦**。

## 先说截图里的文案：问题不是“不够好听”，而是内部模型直接漏给用户了

现在右边的界面实际上是在让用户理解 ArgusFlow 的内部架构：`Action / Locator / BackendPreference / SupportLevel / QueryCost / canonical query / predicate`。`AqlEditor` 里也直接把「原生 / 混合 / 模拟 / 低成本 / 跨后端语义 / 查询语法与谓词类型有效」这些 compiler 词汇呈现出来。

用户真正想表达的是：

> 我要在记事本里找到编辑区域，然后输入这段文字。

而现在产品让他表达的是：

> 我要执行 SetValue，Locator 类型是 Query，Backend Preference 是 UIA，AQL 是……

所以我会把**内部 contract 和界面 vocabulary 完全分开**：

| 当前           | 用户层建议                             | 原因                                 |
| ------------ | --------------------------------- | ---------------------------------- |
| 输出 → 执行动作    | **界面操作 → 点击元素 / 输入文本**            | “Action” 是内部抽象，不是用户任务              |
| 执行动作         | **操作**                            | 避免“执行动作：填写文本”这种机器句式                |
| 填写内容         | **输入内容**                          | 更接近人的表达                            |
| 定位方式         | **查找目标**                          | 用户是在找东西，不是在配置 locator              |
| AQL 语义查询     | **智能查找**，旁边小字 `AQL`               | AQL 是能力，不应该先成为门槛                   |
| 后端偏好         | 默认隐藏；高级设置里叫 **执行引擎**              | UIA/CDP 是实现细节                      |
| 自动规划         | **自动选择（推荐）**                      | “规划”是 planner 术语                   |
| 目标查询         | **查找规则**                          | 比“目标查询”更自然                         |
| 查询语法与谓词类型有效  | **查询可用**                          | 用户不需要知道 predicate typechecking     |
| 查询说明         | **兼容性与性能**                        | 直接回答用户在乎什么                         |
| 原生 / 混合 / 模拟 | **直接支持 / 兼容执行 / 较慢**，技术词放 tooltip | 用户关心效果，不关心 compiler classification |
| 查看规范查询       | 放高级区，叫 **标准化结果**                  | canonical source 基本属于开发者信息         |

甚至 `填写 · AQL` 这种节点摘要也应该消失。画布上更适合出现「**输入文本 · 记事本编辑区**」，AQL 只在展开属性的时候出现。

还有一个更深的问题：后端现在会直接生成面向用户的 `QueryWarning.message: String`，前端拿过来就展示；这相当于把产品文案写进了 Rust analyzer，而且有些字符串还是通过 `{:?}` backend enum 拼出来的。

建议后端只返回：

```text
code: regex_residual_filter
backend: windows_uia
severity: warning
span: ...
params: ...
```

然后由 UI 层决定它展示成「这个条件需要额外筛选，速度可能稍慢」还是专家模式里的「UIA Hybrid / residual filter」。

这样以后换中文、英文、用户模式、专家模式，都不会碰查询内核。

## AQL 格式化 + 染色，我建议不要做一个“高亮 textarea”，而是开始做自己的 Language Service

你现在已经有 lexer → parser → AST → normalize → formatter → analyzer，这已经差不多有一门语言的骨架了。问题是 lexer 的 `Token` 还是 crate-private，parser 最终只输出语义 AST；AST 没保留源码 trivia/span，而 formatter 又是先 `normalize_query()` 再打印。

我会把架构正式升级成：

```text
                         ┌─ Syntax highlight
                         ├─ Diagnostics
Source
  │                      ├─ Completion / Hover
  ▼                      │
Lossless Lexer ──► Recovery CST
                         │
                         └─ Pretty Formatter ─► TextEdit[]
                                  │
                                  ▼
                           Typed HIR / UiQuery
                                  │
                       ┌──────────┴──────────┐
                       ▼                     ▼
                   Normalize            Semantic Analyze
                       │                     │
                       ▼                     ▼
                  Canonical IR       capability / warning
                       │
             ┌─────────┼─────────┐
             ▼         ▼         ▼
           UIA Plan   CDP Plan  Vision Plan
```

这里面最关键的是 **CST 和 HIR 分家**。

你现在的 `UiQuery / QueryExpr` 很适合继续当 HIR，也就是「已经解析、已经类型检查后的语义树」。

但是编辑器需要的是另一个东西：**Lossless CST**。它应该保留 token、空白、源码范围、错误节点，哪怕用户只写到：

```text
button(
  name =
```

它仍然能生成一棵部分语法树，而不是整个 parser `Err(AqlError)` 后什么都没了。

这会直接解锁真正舒服的语法染色、错误波浪线、括号匹配、hover、completion、format range，以及以后 rename/refactor。

---

## 现在的 formatter 有一个我认为需要尽快拆掉的概念耦合

目前：

```rust
pub fn format_query(query: &UiQuery) -> String {
    let normalized = normalize_query(query);
    format_pretty_expression(&normalized.expression, 0)
}
```

也就是说，点击「格式化」不只是改空格和换行，它还会做 predicate 排序、dedup、`any` flatten/dedup、双重 `not` 消除等规范化。

例如用户写：

```text
button(
    name = "保存",
    enabled = true,
    name = "保存"
)
```

“格式化”实际上可能把它变成：

```text
button(
    enabled = true,
    name = "保存"
)
```

语义确实等价，但这已经不是 formatter，而是 optimizer/canonicalizer。

建议以后明确三套 API：

```rust
format_source(...)
canonicalize_query(...)
optimize_query(...)
```

`format_source()` 只决定缩进、换行、空格、括号布局；`canonicalize_query()` 才负责 cache key 和稳定语义表示；如果以后真想做查询优化，再显式叫 `optimize_query()`。

你的设计文档本来就已经把 canonical formatter 当成稳定表示来设计了，工程实现只是目前把它和编辑器“格式化”按钮混到了一起。

## 染色不要只是 lexer token color，可以直接做「语义染色」

基础 token 可以有：

```text
role          button / textbox / window
function      first / nth / any / not / css
property      name / enabled / visible
namespace     uia / dom
operator      = / != / contains / matches
string
regex
number
punctuation
```

但真正让 AQL 编辑器有辨识度的是第二层 semantic decoration。

比如：

```text
button(
    uia.automation_id = "save",
    name matches /保存|Save/i
)
```

可以让 `uia.*` 带一个轻微的 UIA 专用颜色；`matches` 下方出现一个很弱的性能提示；如果当前强制 CDP，则 `uia.automation_id` 直接出现不可执行波浪线；鼠标放上去显示：

```text
UIA     直接支持
CDP     不支持
Vision  不支持
```

这样所谓 capability analyzer 就不再是下面那三个挤成一团的小卡片，而是**直接参与代码编辑体验**。

## 如果真想“自己造”，我反而不建议自己造 contenteditable

真正值得自己造的是 **AQL language engine**，不是 IME、光标、选区、输入法 composition、undo stack。

如果你暂时不想引 CodeMirror / Monaco，我会做一个非常轻量的自研 editor surface：

```text
┌─────────────────────────────┐
│ <pre>         高亮渲染层        │
│ <decorations> 错误/提示层    │
│ <textarea>    原生输入层     │
└─────────────────────────────┘
```

`textarea` 继续负责中文输入法、选区、剪贴板、撤销；把文字 glyph 做透明，只保留 caret 和 selection，下面的 `<pre>` 用同样的 font/line-height 渲染 token。

这样可以自己控制所有染色和 decorations，但不掉进 contenteditable 的坑。

再往上走一步，我会专门建一个：

```text
crates/argusflow-query-wasm
```

让现在这个纯 Rust 的 `argusflow-query` 同时编到 WASM，在 WebView 内直接跑 **同一套 lexer/parser/formatter**。这样键入时可以毫秒级解析，不需要等 Tauri IPC。

现在前端是输入停止 `220ms` 后才 `invoke("inspect_aql")`，对 capability explain 可以，对语法染色就明显太慢了。

理想情况是：

```text
每次输入
  ↓
WASM lexer / parser
  ↓
0~几 ms
syntax color + syntax diagnostic

100~200 ms debounce
  ↓
Rust runtime/context planner
  ↓
UIA/CDP availability + explain
```

本地语言反馈和运行环境分析彻底分开。

## 还有一个以后做染色时一定会踩的大坑：UTF-8 和 JS UTF-16

你现在 `SourceSpan.start/end` 是 **UTF-8 byte offset**。

但是浏览器里的：

```ts
source.slice(start, end)
textarea.selectionStart
```

用的是 UTF-16 code unit。

所以：

```text
button(name = "保存😀")
```

一旦拿 Rust byte offset 直接给 React 做 decoration，范围一定会漂。

现在因为前端只显示「第几行、第几列」，还没暴露出来；等你开始画波浪线、semantic tokens、format edits，这个问题马上出现。

建议 Language Service 对前端明确使用：

```rust
TextRangeUtf16 {
    start: u32,
    end: u32,
}
```

或者统一用：

```text
line + utf16_column
```

Rust 内部依然保持 byte span，协议边界再转换。

# 最近两个 AQL commit，我认为真正值得改的地方

这里有几个已经不是“可以优化一下”，而是会影响后面扩展正确性的结构问题。

| 优先级       | 当前问题                                        | 后果                                              | 我建议                                      |
| --------- | ------------------------------------------- | ----------------------------------------------- | ---------------------------------------- |
| **P0**    | analyzer 用全局 `QueryFeatures` 汇总整棵树          | `any(UIA专用, DOM专用)` 会把两个 backend 都判 Unsupported | capability 必须按 AST 节点递归组合                |
| **P0**    | analyzer 和 backend compiler 各自维护一套能力知识      | 两边已经出现结论不一致                                     | **Plan 是唯一事实来源，Capability 从 Plan 推导**    |
| **P0**    | capability 和 runtime availability 混在 UI 心智里 | UI 显示「UIA 原生、低成本」，实际 execute 还是 unavailable     | 分离 SemanticSupport / RuntimeAvailability |
| **P0/P1** | `plan(action)` 没有 `ExecutionContext`        | 不知道当前是不是 Chrome、有没有 CDP session                 | 恢复设计文档里的 context-aware planner           |
| **P1**    | router 得到的只是两个枚举，execute 又只拿原 Action        | 真执行后必然重新 parse / compile，可能与 planner 漂移         | 返回 PreparedPlan 并直接执行该 Plan              |
| **P1**    | formatter = normalize + pretty print        | 用户操作和 compiler canonicalization 混在一起            | Pretty / Canonical / Optimize 三层分离       |
| **P1**    | parser 是 fail-fast 单错误                      | 无效代码无法继续高亮、completion、多个诊断                      | error-recovery CST + diagnostics[]       |
| **P1**    | `QueryWarning` 直接携带用户字符串                    | Rust domain 层绑 UI 文案和语言                         | code + params + span，UI 做 presentation   |

其中第一个特别值得马上修。

现在 analyzer 是先把整棵树压成：

```rust
specific_backends: BTreeSet<QueryBackend>
has_css
has_regex
has_any
has_not
...
```

然后 UIA 只要看到整个 query 的 `specific_backends` 里存在 `BrowserCdp` 就直接 Unsupported，CDP 反过来也一样。

所以这类非常合理的 AQL：

```text
any(
    button(uia.automation_id = "save"),
    button(dom.test_id = "save")
)
```

按你定义的 `any`「按顺序的 fallback」语义，本应该：

```text
UIA → 第一支可执行
CDP → 第二支可执行
```

但目前的 feature-bag analyzer 会把 backend-specific 信息做成全集合，两个 backend 都会因为看到“另一个 backend 的属性”而判掉。

这说明 analyzer 不能继续靠全局 bool feature 发展。

应该变成类似：

```text
Capability(Match)      = backend.compile_matcher(...)
Capability(Child)      = combine(parent, target)
Capability(Descendant) = combine(ancestor, target)
Capability(Any)        = choose_best_supported_branch(...)
Capability(Not)        = emulate(child)
Capability(First)      = child + selection cost
```

也就是 **capability algebra**。

## 而且 analyzer/compiler 已经发生第一次“事实分裂”了

`analyze.rs` 把 `NotEqual` 算进 `has_residual_text`，所以 UIA 会认为：

```text
name != "取消"
```

是 `Hybrid`。

但 UIA compiler 明确把：

```rust
MatchOperator::Equal | MatchOperator::NotEqual
```

都塞进 `pushdown`。

也就是说，同一个查询：

```text
Analyzer:
    UIA = Hybrid

Compiler:
    NotEqual = native pushdown
```

现在只是 UI 标签不准；以后规则越来越多，两个知识库一定越来越漂。

所以我建议把架构倒过来：

```text
BackendCompiler.compile(query, context)
             │
             ▼
         QueryPlan
             │
       ┌─────┴─────┐
       ▼           ▼
   summary()     explain()
       │
       ▼
Capability / Cost / Warnings
```

**不要再让 analyzer 猜 backend compiler 能做什么。**

backend compiler 自己生成真实 plan，然后从真实 plan 得出：

```text
Native / Hybrid / Emulated
cost
required properties
round trips
residual filters
runtime requirements
```

这会比现在稳很多。

---

## ActionRouter 也可以再抽象一层，这可能是这两次提交里最值得“再牛逼一点”的地方

你的设计文档其实已经写对了：planner 应该拿 `ExecutionContext`，包括活动应用、CDP session、窗口、缓存状态等。

但当前 trait 还是：

```rust
fn plan(&self, action: &AutomationAction) -> ActionCapability;
async fn execute(&self, action: &AutomationAction) -> ...
```

而且通用 `argusflow-agent` 直接依赖了 AQL 的 `QueryCost` 和 `SupportLevel`。

我更倾向于：

```rust
trait ActionBackend {
    fn prepare(
        &self,
        action: &AutomationAction,
        context: &ExecutionContext,
    ) -> Result<PreparedCandidate, PlanRejection>;
}
```

`PreparedCandidate` 里面已经有：

```text
backend
score
quality
cost
explain
runtime requirements
真正准备执行的 compiled plan
```

Router 排完之后直接：

```text
candidate.execute()
```

而不是：

```text
plan(original action)
...
execute(original action)
```

这么做有个非常大的好处：

> **UI 里 Explain 的 Plan，就是最后真正执行的 Plan。**

不存在 analyzer 说一套、router 排一套、backend execute 又重新 parse 一套。

---

## 另外，当前 UI 有个非常容易让用户产生错误预期的问题

现在 UIA/CDP 的 `plan()` 已经能够说自己是 Native / Hybrid，但 `execute()` 两边实际上都还是直接返回 `BackendUnavailable`。

所以截图里的：

> UIA：原生 / 低成本

现在准确含义其实只是：

> **“从静态语义上，这个查询未来可以被 UIA 原生实现。”**

而用户看到的含义会是：

> “它现在能通过 UIA 原生执行。”

这两件事差很多。

建议能力模型马上拆成：

```text
Semantic support
    Native / Hybrid / Emulated / Unsupported

Runtime availability
    Ready / Unavailable / MissingContext / NotImplemented
```

这样 UI 可以显示：

```text
UIA
语义：直接支持
状态：尚未接入执行器
```

开发期尤其重要，不然界面比真实能力成熟得太快。

---

如果只让我选一个下一阶段主线，我会按：

**Lossless CST / Language Service → Plan-derived capability → PreparedPlan + ExecutionContext → 新 AQL Editor → 最后统一重写产品文案**

这个顺序走。

这样 AQL 不会只是“一个能 parse 的 DSL”，而会逐渐长成 ArgusFlow 自己的 **UI Query Compiler + Language Server + Query Optimizer**。

而且你现在底子其实已经够了，不需要推翻：`UiQuery/QueryExpr`、独立 `argusflow-query` crate、UIA/CDP Plan、版本化 `AqlQuery` 这些都应该保留。真正要做的是在它们之间补上 **CST、prepared plan、context、presentation model** 这四层。

如果你下一步准备直接动代码，我比较建议先从 **`argusflow-query` 的 CST + 新 formatter API** 开始，这一刀做好以后，染色、诊断、completion、format-on-type、hover 基本都会顺着长出来。
