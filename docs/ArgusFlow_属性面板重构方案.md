# ArgusFlow 属性面板重构方案

> 目标：参考当前 `docs/方案.md` 与 `docs/优化方案.md` 的表达方式，给出右侧节点属性面板的产品与工程重构建议。
> 重点：把“执行引擎参数面板”转成“任务意图面板”，降低 OCR / UIA / CDP / AQL 等底层概念对普通用户的干扰。
> 适用：当前截图中的“操作界面 / 点击 / 选择联系人”场景，并尽量推广到输入、检查、等待等 UI 自动化节点。

## 1. 结论先行

当前右侧属性面板最大的障碍不是视觉，而是抽象层级：用户要配置任务意图，界面却要求理解执行引擎参数。
用户真正想表达的是“在微信中找到‘选择联系人’，然后单击”，而不是 scope、locator、backend、poll interval。
因此建议把属性面板从 Runtime Config Editor 重构为 Intent Editor。
主面板只回答四个问题：在哪里、找什么、做什么、找不到怎么办。
UIA、CDP、OCR、Vision、AQL、fallback 等能力继续保留，但收束到主路径之后的“执行方式”和“开发者信息”；大段原始配置使用独立对话框承载。
核心原则：先表达任务意图，再紧凑呈现实现信息，不用层层折叠隐藏内容。

## 2. 当前信息架构的问题

当前结构主要是“基本信息 / 设置 / 输出”，其中“设置”包含动作、范围、应用节点、查找方式、执行方式、等待参数。
这种结构非常接近后端数据模型，却不符合用户的自然思考顺序。
用户不会先思考 scope，再思考 app node，再思考 locator backend。
用户更自然的顺序是：我要做什么、我要对谁做、它在哪里、失败时怎么办。
因此右侧属性面板应该围绕任务语义重新分组，而不是围绕字段来源分组。

## 3. 最难懂的一组字段

当前最需要优先重构的是“查找方式 + 编辑查找条件 + 执行方式”。
“按界面内容查找”和“屏幕文字（OCR）”在普通用户看来高度重叠。
真正重要的目标内容却被藏在“编辑查找条件”按钮后面。
OCR 本质是定位后端，不应该成为用户配置目标时的首要选择。
用户应该选择“我要找什么”，系统再决定“用什么找到它”。

## 4. 新的一级结构

推荐一级结构：概览、做什么、找什么、找不到时、输出、执行方式、开发者信息。
“概览”展示节点名称与人类可读任务摘要。
“做什么”只描述动作，例如单击、双击、输入文本、悬停。
“找什么”描述应用、目标类型、目标内容以及匹配状态。
“找不到时”描述等待、超时与失败策略。
“执行方式”展示定位引擎、动作引擎与重试间隔；“开发者信息”直接展示紧凑元数据，并通过对话框查看原始配置。

## 5. 顶部任务摘要

顶部应该优先出现一句任务摘要，而不是内部编号和节点类型。
示例：`在「微信」中找到文字「选择联系人」，然后单击。`
示例：`在记事本中找到编辑区域，然后输入「Hello World」。`
示例：`等待「登录成功」出现，最多等待 10 秒。`
摘要应该根据当前配置自动更新，让用户无需扫描整张表单就能确认节点含义。

## 6. 任务摘要可交互

摘要可以进一步设计成结构化句子：`在 [微信] 中找到 [文字] [选择联系人]，然后 [单击]`。
其中“微信”“文字”“选择联系人”“单击”都可以点击修改。
这种设计可以成为极简编辑入口，同时保留下方完整表单。
它比静态说明更有价值，因为用户可以直接从自然语言表达切入配置。

## 7. 基本信息降级

当前“节点名称 / 内部编号 / 类型”不应该拥有相同视觉权重。
节点名称保留在顶部，并允许自动生成。
内部编号 `select_contact` 移入“开发者信息”。
节点类型“操作界面”也移入开发者信息，并建议只读。
工程元数据不应该与用户任务争夺第一屏注意力。

## 8. 区块命名

“设置”这个区块名过于宽泛，无法帮助用户判断内容。
建议改成“做什么”“找什么”“找不到时”。
这些标题本身就是问题，用户能立即知道每组字段解决什么。
相比抽象名词，更推荐直接的任务语言。

## 9. 动作字段

“操作”建议改为“动作”。
“点击”建议进一步明确为“单击”，方便与“双击”“右键”区分。
动作列表不应该永远展示完整 enum，而应该根据目标能力过滤。
例如输入框可以提供输入文本、清空、聚焦；复选框可以提供勾选、取消勾选、切换。

## 10. 在哪里执行

“操作范围”建议改成“在哪里”，或者直接合并为“应用 / 窗口”。
如果绝大多数动作都发生在具体应用里，可以不再单独展示“指定应用”这一层。
可选范围可包括：当前窗口、指定应用、整个桌面、指定区域。
这比“操作范围”更符合普通用户语言。

## 11. 应用节点

“应用节点：打开微信”暴露了流程图内部引用关系。
用户首先关心的是“微信”，不是“打开微信这个上游节点”。
建议主字段显示 `应用 / 窗口：[微信]`。
下方弱化显示 `来源：打开微信`，必要时 hover 显示节点 ID。

## 12. 应用选择器

应用下拉可以同时展示应用名、图标、来源节点与运行时绑定状态。
例如：`微信 / 来自：打开微信 / 运行时绑定`。
复杂流程里，这比只显示上游节点名称更容易理解。
当前窗口和整个桌面可以作为不依赖上游节点的特殊选项。

## 13. 查找方式改为目标类型

“查找方式”建议重构为“目标类型”。
推荐选项：自动、控件、文字、图片、网页元素、坐标、区域。
这里表达的是用户要找的对象，而不是引擎使用的算法。
目标类型与定位后端是两个维度，不能继续混在同一层。

## 14. 自动目标类型

对新用户可以提供“自动（推荐）”。
系统根据拾取结果、应用环境和已有条件判断目标语义。
例如 Chrome 的 DOM 元素优先转成网页元素，Windows 控件优先转成控件。
纯可见文字可以转成文字目标，并允许 UIA Name、DOM Text、OCR 多种实现。

## 15. 目标内容必须直显

当前“编辑查找条件”隐藏了最重要的信息，建议取消这种二次入口。
文字目标直接展示：`文字：[选择联系人]`。
控件目标直接展示角色、名称等核心条件。
图片目标直接展示缩略图，坐标目标直接展示 X/Y。
目标条件应该成为表单本体，而不是藏在按钮后面。

## 16. 更多条件

“编辑查找条件”可以改造成“+ 添加条件”或“更多条件”。
基础规则只显示最常用条件。
复杂条件再追加可见性、父级、区域、第几个、Automation ID 等。
这属于渐进式披露：简单任务简单，复杂任务仍然可表达。

## 17. 文字目标表单

文字目标推荐字段：文字、匹配方式、可选区域。
示例：`文字 [选择联系人]`，`匹配 [完全匹配]`。
匹配方式使用用户语言：完全匹配、包含、开头是、结尾是、正则表达式。
不要在普通界面直接展示 equals、contains、regex 等内部枚举。

## 18. 屏幕重新选择

属性面板应该始终提供明显的 `在屏幕上重新选择` 入口。
RPA 的自然交互是指向目标，而不是手写 locator。
用户进入拾取模式后，鼠标悬停目标高亮，点击后自动生成条件。
系统应尽量生成稳定语义条件，而不是直接保存绝对坐标。

## 19. 拾取后的信息处理

拾取一个按钮时，系统内部可能得到 UIA Name、ControlType、AutomationId、Bounds、OCR Text 等。
这些信息不应该全部原样塞给用户。
主界面只展示系统认为最稳定、最容易理解的一组条件。
其余证据与 fallback 可以放进执行方式和诊断界面。

## 20. 目标实时状态

目标区域应该持续告诉用户“现在能不能找到”。
唯一匹配：`✓ 当前找到 1 个目标`。
多个匹配：`⚠ 当前找到 3 个目标，需要增加条件`。
没有匹配：`○ 当前未检测到目标，运行时将最多等待 5 秒`。
这比长篇解释 OCR/UIA 的工作原理更能降低不确定性。

## 21. 多个目标的处理

找到多个目标时不能只报错，还应直接给修复入口。
可以提供“添加条件”和“选择其中一个”。
选择其中一个后，在目标应用上高亮候选并编号。
用户点选候选后，系统自动增加父级、区域、Automation ID 或索引等区分条件。

## 22. 定位稳定性

可以给 locator 一个轻量稳定性提示：高、一般、脆弱。
AutomationId、Role + Name 通常更稳定，纯文本与 OCR 次之，绝对坐标最脆弱。
稳定性只是辅助信号，不能成为用户必须理解的评分系统。
第一版可以不做，等目标检查与运行历史稳定后再增加。

## 23. OCR 的位置

“执行方式：屏幕文字（OCR）”建议从主面板移除。
在主路径之后的“执行方式”中改成“定位引擎：自动（推荐）”。
系统可额外显示“当前使用：OCR”或“当前计划：UIA → OCR”。
这样保留技术透明度，但不会让普通用户先学习 OCR。

## 24. 定位与动作执行拆分

OCR 属于定位方式，而不是动作执行方式。
真正的动作执行后端可能是 UIA Invoke、DOM click、SendInput Mouse Click。
因此“执行方式”中最好明确区分“定位引擎”和“动作引擎”。
这也更符合 ArgusFlow 后续 planner 的真实模型。

## 25. 执行方式与开发者信息

技术信息不再放进可折叠的“高级设置”，而是拆成直接可见的“执行方式”和“开发者信息”。
定位：自动、UIA、CDP、OCR、Vision，以及当前 planner 计划。
动作：自动、Invoke、DOM Action、SendInput 等。
等待与重试：重试间隔、策略；开发者信息：内部编号、节点类型与画布信息。原始配置通过独立对话框查看，避免 JSON 撑长侧栏。

## 26. 等待目标出现

“找不到目标时等待”建议改为“等待目标出现”。
表达更短、更自然，也更接近用户意图。
主界面默认开启，并把超时放在同一区域。
如果节点类型本身是“检查是否存在”，则可以默认关闭或使用更短超时。

## 27. 时间单位

“最长等待 5000 毫秒”应该改成“最多等待 5 秒”。
毫秒是运行时单位，不应该成为普通配置单位。
内部仍可保存 timeoutMs，UI 负责秒与毫秒转换。
高级模式如果需要，可以允许切换 ms / s / min。

## 28. 检查间隔

“检查间隔 200ms”默认应该隐藏。
绝大多数用户不知道 100、200、500ms 的实际差异，也不应该替引擎调度 polling。
建议放入主路径之后的“执行方式”并改名为“重试间隔”。
如果以后引入 UIA 事件驱动，甚至可以进一步抽象为“等待策略”。

## 29. 失败策略

“找不到时”未来可以支持更完整策略：等待目标、最多等待、超时后怎么办。
超时后选项可以包括让节点失败、继续执行、跳过节点、走失败分支、重新尝试。
第一版保留“节点失败”默认值即可，不需要一次性做完所有策略。

## 30. 运行中的等待反馈

节点执行时画布上可以显示 `等待目标… 3.2s / 5s`。
找到后显示 `已找到 · 1.8s`。
超时后显示 `目标未出现`。
这能让属性面板的等待配置与运行状态形成一致心智。

## 31. 推荐主面板

推荐第一版主面板字段顺序：节点名称、任务摘要、动作、应用/窗口、目标类型、目标内容、匹配、重新选择、目标状态、等待目标出现、最多等待。
输出使用标题行摘要，空状态不再绘制占位框；执行方式和开发者信息直接紧凑展示，不设置折叠门槛。
这种布局把真正需要用户决定的内容集中在第一屏。
主路径不出现内部编号、节点类型、OCR、UIA、poll interval。

## 32. 极简版本

更激进的版本可以只显示：`在 [微信] 中找到 [文字] [选择联系人]，然后 [单击]`。
下方只有“在屏幕上重新选择”“找到 1 个”“等待最多 5 秒”，再顺序展示紧凑的输出、执行方式与开发者信息。
这种方案非常适合 80% 的简单任务。
复杂条件通过独立 AQL 编辑器进入结构化编辑，不在侧栏制造嵌套层级。

## 33. 不要过度 AI 化

属性面板可以使用自然语言摘要，但不建议第一版直接改成纯聊天框。
ArgusFlow 的核心价值仍然包括确定性、结构化、可调试、可复现。
推荐“结构化表单 + 自然语言摘要”，而不是完全由自由文本驱动。
AI 可以负责生成意图，但最终仍落到可检查的结构化配置。

## 34. AQL 的产品位置

AQL 更适合作为高级能力和稳定中间表示，而不是普通用户的默认门槛。
普通模式通过表单生成 UiQuery/AQL。
专家模式可以直接编辑 AQL。
同一目标可以在“可视化规则”和“AQL 编辑”之间切换。

## 35. AQL 查看入口

可以在“找什么”标题旁提供 `编辑 AQL 查询`。
点击后直接在工作区 Dock 打开独立 AQL 编辑器，例如显示 `button(name = "选择联系人")`。
侧栏继续保留可逆的基础字段，不在其中嵌套第二层规则面板。
这样新用户不需要懂语法，高级用户仍然拥有完全控制能力。

## 36. 复杂 AQL 的可逆性

如果用户写了 any、not、跨后端谓词等复杂表达式，可能无法完整映射回基础表单。
切换回基础模式时必须明确提示可能丢失表达能力。
优先保持 AQL，不应静默简化或删除条件。
表单与 AQL 最好共用同一个语义模型，而不是两套独立状态。

## 37. 用户词汇与引擎词汇

建议明确区分产品 vocabulary 与 engine vocabulary。
用户层使用动作、目标、应用、文字、按钮、等待、超时、找到、未找到。
引擎层使用 Action、Locator、Scope、Backend、Planner、UIA、CDP、OCR、Polling、Fallback。
主界面使用第一层，执行方式、诊断与开发工具使用第二层。

## 38. 统一字段词典

建议前端建立统一字段词典，避免不同节点对同一概念使用不同名称。
例如 action → 动作，target → 目标，backend → 定位引擎，timeout → 最多等待。
目标、控件、元素也需要统一定义：目标是通用概念，控件偏 UIA，元素偏 Web/DOM。
统一词汇会显著降低节点之间的学习成本。

## 39. 节点自动命名

节点名称可以根据配置自动生成，例如“点击选择联系人”“输入手机号”“等待登录成功”。
默认 `nameMode = auto`，用户手动改名后切换为 manual。
manual 状态下后续目标变化不覆盖用户名称。
可以提供“恢复自动命名”。

## 40. 节点摘要同步

任务摘要应随动作、应用、目标变化即时更新。
例如动作从单击改为双击，摘要同步变成“双击微信中的‘选择联系人’”。
这种即时反馈能帮助用户发现配置错误。
摘要生成逻辑可以独立成 formatter，方便画布节点复用。

## 41. 控件形态

不要让每一行都变成下拉框。
动作适合下拉，文字目标适合输入框，等待适合开关，时间适合数字 + 单位，状态适合 badge。
高频且选项少的目标类型可以使用 segmented control。
视觉控件多样化能降低“每个字段都要选择”的心理负担。

## 42. 输出区域

输出区域直接展示标题摘要，并根据节点类型展示真正有价值的结果；没有额外输出时不渲染空占位框。
点击节点可能输出 success、matched_target、duration。
读取文本节点可以输出 text 与 target。
不应该为了统一 schema 而展示大量用户不会引用的底层字段。

## 43. 面板布局

窄面板优先使用可伸缩的 label / control 比例行，让短标签与控件在同一视觉行内完成阅读；空间不足时再自然换行。
标签列不得使用僵硬的固定宽度，控件列需要保留最小可操作宽度，并适配中文长标签、帮助文字、错误信息与国际化。
section 间距应明确但克制，字段之间使用紧凑节奏，让分组一眼可见又不浪费纵向空间。
属性面板宽度可以适度增加或支持拖拽，但优先级低于信息架构。

## 44. 帮助文字

帮助文案要短，一行只回答一个问题。
`来源：打开微信` 解释对象来源。
`当前使用 OCR` 解释执行计划。
`找到 1 个目标` 解释当前匹配结果。
详细技术说明放 tooltip、诊断或独立配置对话框，不要堆在主表单。

## 45. 状态颜色

状态色应该表达成功、警告、错误、未检查，而不是 UIA/OCR/CDP 技术类别。
技术类别可使用小 badge，例如 `[UIA] → [OCR]`。
避免用过多颜色要求用户记忆技术含义。
视觉重点应放在任务是否可执行。

## 46. 节点不存在状态

截图底部显示“节点不存在”，右侧却仍可编辑，这是明显的状态矛盾。
selectedNodeId 找不到时，Inspector 应整体进入 missing 状态或直接关闭。
missing 状态只显示“此节点已被删除或无法找到”和关闭按钮。
不要让幽灵节点继续接受配置修改。

## 47. Inspector 状态机

建议明确至少 idle、selected、validating、missing、running、error 等状态。
selected 正常编辑；validating 检查目标；missing 节点失效；running 执行中；error 配置错误。
状态应该驱动整个面板，而不是不同子组件各自判断。
这会减少当前编辑器、画布、属性面板之间状态不一致的问题。

## 48. 运行时修改

节点运行时需要明确字段是否允许修改。
可以锁定关键目标字段，或者提示“修改只影响下一次运行”。
无论选择哪种策略，都要保持一致，不要让用户误以为正在执行的 plan 会实时改变。
运行状态与编辑状态应明确区分。

## 49. 目标验证

用户输入条件后可以 debounce 做轻量验证。
昂贵 OCR 不需要每个字符触发，可以在停止输入后或用户点击“检查目标”时执行。
提供“检查目标”按钮后，可显示 match count 与“在屏幕上高亮”。
第二阶段可以进一步做实时 overlay 高亮。

## 50. 目标预览

拾取后可以直接提供紧凑的目标预览；信息较多时使用独立预览浮层，而不是再增加折叠层级。
UIA/DOM 目标显示角色、名称、应用；OCR/图片目标显示裁剪截图。
预览用于确认“我选的到底是不是这个”。
默认不宜占用太多空间。

## 51. 条件 chips

复杂定位条件可以用 chips 展示，例如 `[按钮] [名称: 选择联系人] [可见] [+]`。
这非常适合把 AQL 的 predicate 可视化。
点击 chip 编辑具体条件，点击加号新增条件。
它比长表单更适合中等复杂度 locator。

## 52. 后端自动规划

UIA、CDP、OCR 不应该是默认互斥模式，很多场景更适合 fallback 链。
例如文字目标可以优先 UIA Name，失败后再 OCR。
因此默认 `backendPreference = auto`，由 planner 结合 ExecutionContext 生成计划。
用户只有在排障或特殊场景下才强制指定后端。

## 53. Planner explain

Planner 应该返回适合 UI 消费的结构化 explain 数据，而不是长字符串。
例如 status、primary、fallbacks、stability、warnings。
普通界面把它翻译成“可以稳定定位”或“需要视觉识别，速度可能稍慢”。
专家模式再显示 UIA → OCR、runtime availability 等技术信息。

## 54. 诊断模型

后端 warning 建议返回 code + params + span，而不是直接生成中文句子。
前端可以统一把 `multiple_matches` 显示为“找到 3 个目标，需要增加条件”。
诊断应尽量绑定具体字段，只有全局问题才放顶部 banner。
warning、error、info 也要区分，不要所有问题都红色。

## 55. 配置状态与运行状态

“规则有效”与“当前找到目标”是两个不同维度。
可以分别展示：`配置 ✓ 有效`，`当前环境 ○ 暂未找到`。
不要因为当前 UI 里没有目标，就把一个合法等待节点标成配置错误。
也不要把当前找到一次目标描述成“一定可以运行”。

## 56. 运行历史

未来可根据最近运行历史计算定位稳定性，例如成功 10/10、平均 120ms。
如果经常失败，可以建议增加条件或使用更稳定 locator。
这属于后续增强，不建议阻塞第一版重构。
第一版更重要的是字段重组和目标状态反馈。

## 57. 第一阶段：只改前端

第一阶段建议不改 workflow schema、不改 runtime、不改 planner contract。
只做 Inspector 重排、字段重命名、目标摘要、秒单位、技术区平铺、任务摘要。
通过 Adapter 把现有 engine 字段映射成新的 Intent ViewModel。
这是成本最低、收益最高、风险最可控的一步。

## 58. 第二阶段：目标检查

第二阶段增加 Check Target、Match Count、Highlight、Target Picker。
Runtime 提供 inspect target 与候选信息。
前端增加 TargetStatus、CandidateList、重新拾取与高亮按钮。
这一阶段会把“我不知道能不能找到”的不确定性大幅降低。

## 59. 第三阶段：Intent 到 Planner

第三阶段真正建立 User Intent → UiQuery/AQL → Planner → Prepared Plan → Action。
Inspector 只编辑意图与语义目标。
BackendPreference 从普通配置中进一步退居高级模式。
Planner 成为后端选择与 fallback 的唯一事实来源。

## 60. ViewModel 建议

建议新增 ActionInspectorViewModel，而不是 React 组件直接读写所有 engine 字段。
ViewModel 至少包含 summary、action、location、target、recovery、execution。
Target 使用 discriminated union：TextTarget、ControlTarget、ImageTarget、WebTarget、CoordinateTarget。
这样 TargetEditor 可以按 target.type 渲染，而不是按 backend 判断。

## 61. 适配层

短期结构可以是 `Existing Workflow Node → Inspector Adapter → Intent ViewModel → New Inspector UI`。
保存时反向映射回现有 Workflow Node。
这样 UI 可先完成重构，而无需同步推翻旧存储格式。
后续 schema 真正语义化时，再替换 Adapter 内部实现。

## 62. 组件拆分

推荐组件：NodeInspector、InspectorHeader、IntentSummary、ActionSection、TargetSection、RecoverySection、OutputSection、ExecutionSection、DeveloperSection。
TargetSection 下再拆 AppPicker、TargetTypePicker、TextTargetEditor、ControlTargetEditor、ImageTargetEditor、TargetStatus。
复杂度最大的部分应该集中在 TargetSection。
不要把全部条件继续堆进一个巨大 Inspector 组件。

## 63. 文本目标编辑器

TextTargetEditor 可以包含文字、匹配方式、区域与更多条件。
普通模式只展示文字与匹配。
高级条件再加入大小写、区域、父级等。
UI 不应该因为最后使用 OCR，就换成完全不同的一套目标表单。

## 64. 控件目标编辑器

ControlTargetEditor 可以展示控件类型、名称与“添加条件”。
更多条件可以包括 Automation ID、Class Name、可见、启用、父级。
拾取后优先自动生成稳定条件。
如果当前应用不支持 UIA，可以由 planner 选择其他实现，而不是强迫用户换目标类型。

## 65. 图片与坐标

ImageTargetEditor 展示目标图片、重新截取、匹配精度；执行方式区域再放阈值、ROI、缩放。
CoordinateTargetEditor 展示 X、Y、相对范围与“从屏幕选择”。
坐标目标应明确提示“窗口移动后可能失效”。
不同目标类型共享同一个总体信息架构。

## 66. 统一点击节点

产品层尽量避免 OCR 点击、UIA 点击、网页点击、图片点击等大量 backend-specific 节点。
更推荐统一成“点击”，目标类型和 planner 决定定位与执行方式。
执行方式仍允许强制后端，所以默认简单并不等于失去控制。
这与 AQL 统一查询语言的方向是相符的。

## 67. 专家模式

未来可以考虑简洁、标准、专家三种属性面板模式。
简洁只展示动作、目标、等待；标准增加更多条件与输出；专家展示 AQL、Backend、Planner、Raw JSON。
第一版不必真的做三种全局模式，使用紧凑的执行方式、开发者信息与独立配置对话框即可控制信息密度。
避免过早增加设置项本身的复杂度。

## 68. Happy Path

理想流程：拖入点击节点 → 右侧显示“还没有选择目标” → 点击“在屏幕上选择” → 点微信中的“选择联系人”。
ArgusFlow 自动识别应用、目标类型与条件。
面板回填“动作：单击 / 应用：微信 / 目标：文字‘选择联系人’ / ✓ 找到 1 个”。
用户直接运行，整个主路径无需出现 OCR、UIA、5000ms、200ms。

## 69. Debug Path

只有当执行失败时，用户才需要关注执行方式与诊断信息。
这时可直接查看当前计划，并从诊断界面查看最近错误、fallback、定位耗时、runtime availability。
用户可以重新选择目标、增加条件、延长等待或强制其他引擎。
技术细节应该服务于排障，而不是成为创建节点的前置知识。

## 70. 与 AQL 架构的关系

ArgusFlow 已经在走“语义查询 → planner → UIA/CDP/Vision”的路线。
Studio 如果仍要求用户人工选择 backend，就没有充分利用这个架构。
更合理的是用户描述目标，AQL 作为稳定语义表示，planner 负责执行计划。
底层能力越复杂，上层界面反而应该越简单。

## 71. AI 生成流程

未来 AI 根据自然语言生成流程时，也应该生成 ActionIntent 与 TargetIntent。
例如“打开微信，然后点选择联系人”不应该让模型猜 OCR、poll interval、timeoutMs。
这些运行参数由系统默认值与 planner 决定。
这会让 AI 生成 workflow 更稳，也更容易解释。

## 72. 字段迁移优先级

P0：重构查找方式/执行方式、目标条件直显、时间单位改秒、内部编号下沉、任务摘要。
P1：目标检查、屏幕拾取、多目标诊断、当前 planner 计划。
P2：实时高亮、AQL 双向编辑、稳定性评分、运行历史、专家模式。
不要让 P2 的理想能力阻塞 P0 的简单改进。

## 73. 字段重命名表

`操作 → 动作`。
`操作范围 → 在哪里` 或直接合并到 `应用 / 窗口`。
`应用节点 → 应用 / 窗口`，来源节点作为弱提示。
`查找方式 → 目标类型`。
`执行方式 → 定位引擎`，放在主路径之后的紧凑技术区。
`找不到目标时等待 → 等待目标出现`。
`最长等待 → 最多等待`。
`检查间隔 → 重试间隔`，放在“执行方式”。

## 74. 推荐 P0 UI

顶部：选择联系人。
摘要：在微信中找到“选择联系人”并单击。
做什么：动作 = 单击。
找什么：应用/窗口 = 微信；目标类型 = 文字；文字 = 选择联系人；匹配 = 完全匹配。
找不到时：等待目标出现；最多等待 5 秒。
输出显示“使用默认结果”摘要；执行方式与开发者信息直接平铺，原始配置由“查看配置”对话框承载。

## 75. 可用性测试

找一个完全不了解 ArgusFlow 的用户，要求 30 秒内完成“在微信里点击‘选择联系人’”。
如果用户继续问“查找方式和执行方式有什么区别”“为什么是 OCR”“应用节点是什么意思”，说明重构没有完成。
理想结果是用户只需要理解单击、微信、选择联系人、等待 5 秒。
再用记事本输入文本、等待登录成功两个任务验证通用性。

## 76. 可观测指标

可以统计节点首次配置完成时间、字段回退次数、查看原始配置次数、重新选择目标次数、运行失败率、多目标错误率。
如果用户频繁查看原始配置或强制执行引擎，说明默认 planner 或普通表单仍不足。
如果用户经常强制 backend，说明自动规划需要改进。
这些数据可以帮助后续迭代，而不是凭感觉持续增加字段。

## 77. 产品原则

不要以“设置项越多越专业”为目标。
底层能力越多，越应该通过合理默认、自动规划和渐进式披露降低认知负担。
用户配置的是意图，系统负责规划。
默认展示结果，按需展示实现。
错误不仅要说明发生了什么，还要告诉用户怎么修。

## 78. 最终判断标准

以后每新增一个字段，都先问：用户需要决定这件事吗？
如果系统可以可靠自动决定，它默认就不应该出现在主面板。
再问：用户现在需要知道这件事吗？如果只有出问题时才需要，就放执行方式、开发者信息或诊断界面。
只有真正属于用户意图的字段，才进入第一屏。
这条规则可以长期约束 ArgusFlow 属性面板的复杂度。

## 实施检查清单

- [ ] 主面板不再同时出现“查找方式”和“执行方式”。
- [ ] 当前目标内容始终可以在第一屏直接看到。
- [ ] OCR / UIA / CDP 移入主路径之后的“执行方式”。
- [ ] timeout 默认以秒展示，而不是毫秒。
- [ ] poll interval 默认隐藏。
- [ ] 内部编号与节点类型进入开发者信息。
- [ ] 顶部生成可读任务摘要。
- [ ] 应用字段首先显示应用名，而不是来源节点名。
- [ ] 新节点优先提供“在屏幕上选择目标”。
- [ ] 找到 0 / 1 / 多个目标时有明确状态反馈。
- [ ] 节点 missing 时属性面板不再允许继续编辑。
- [ ] 属性修改纳入统一 Undo / Redo。
- [ ] 第一阶段通过 Adapter 映射到当前 workflow schema。

## 推荐实施顺序

1. 先重排字段和文案，不改后端。
2. 再做任务摘要、目标摘要和无折叠的紧凑技术区。
3. 再做目标检查与候选数量反馈。
4. 再接屏幕拾取和 overlay 高亮。
5. 最后把 Visual Target、AQL、Planner 与 Prepared Plan 正式串起来。

## 最终一句话

ArgusFlow 的右侧属性面板应该让用户感觉自己是在描述一个任务，而不是填写一份执行引擎配置表。

```text
用户说：在微信里点“选择联系人”。
ArgusFlow 负责：理解目标 → 生成语义查询 → 选择后端 → 等待 → 定位 → 执行动作 → 提供诊断。
```

只要这条边界守住，未来底层增加 UIA、CDP、OCR、Vision 或新的执行后端，右侧面板也不必同步变得越来越复杂。
