# 1. Windows 控件：不要用现成 RPA wrapper

直接 Rust 调：

```text
UIAutomationCore.dll
```

使用微软原生：

```cpp
IUIAutomation
IUIAutomationElement
IUIAutomationCondition
IUIAutomationCacheRequest
IUIAutomationInvokePattern
IUIAutomationValuePattern
...
```

Rust 侧直接用微软自己的 `windows-rs`。微软官方的 `windows` crate 就是 typed C/COM/WinRT Windows API bindings，非常适合干这件事。([GitHub][1])

也就是说别：

```text
Rust
 ↓
第三方 uiautomation wrapper
 ↓
另一层 abstraction
 ↓
COM
```

如果你追求极限，直接：

```text
Rust
 ↓
windows-rs
 ↓
IUIAutomation COM
 ↓
UIAutomationCore.dll
```

你的核心可以类似：

```rust
pub struct UiaEngine {
    automation: IUIAutomation,
}

impl UiaEngine {
    pub fn find(&self, selector: &Selector) -> Result<Element> {
        // build IUIAutomationCondition
        // FindFirst / FindAll
    }
}
```

微软 UI Automation 本身就是为了让客户端获取 UI tree、控件属性以及通过 control pattern 操纵 UI。([Microsoft Learn][2])

## 真正影响性能的是：Cache

千万不要这样：

```rust
element.name()?;
element.control_type()?;
element.bounds()?;
element.enabled()?;
element.automation_id()?;
```

因为这有可能意味着很多跨进程 UIA 调用。

应该一次请求：

```text
CacheRequest
 ├── Name
 ├── AutomationId
 ├── ControlType
 ├── BoundingRectangle
 ├── IsEnabled
 ├── InvokePattern
 └── ValuePattern
```

然后一次拿回来。

Windows UIA 的事件 API本身也允许配合 `IUIAutomationCacheRequest` 注册事件。([Microsoft Learn][3])

于是：

```text
❌ polling

while !exists("Save") {
    sleep(100ms)
    scan_tree()
}
```

改成：

```text
✅ events

StructureChanged
     ↓
UIA callback
     ↓
cached element
     ↓
selector matcher
     ↓
立即唤醒 task
```

微软现在甚至明确建议 UI Automation 客户端优先考虑 **event handler groups** 来注册事件监听器。([Microsoft Learn][4])

这个优化比“Rust 比 C# 快多少”重要得多。

# 2. 点击按钮：优先 Invoke，不要模拟鼠标

比如：

```text
[ 保存 ]
```

找到之后不要第一反应：

```rust
move_mouse(x, y);
click();
```

而应该：

```text
IUIAutomationInvokePattern::Invoke()
```

UI Automation 的 `InvokePattern` 就是用于直接激活控件动作。([Microsoft Learn][5])

所以你的 action priority 应该是：

```text
InvokePattern
      ↓ 不支持
SelectionItemPattern
      ↓
TogglePattern
      ↓
ExpandCollapsePattern
      ↓
ValuePattern
      ↓
LegacyIAccessiblePattern
      ↓
SendInput
```

这会非常快。

而且不要求：

```text
鼠标真的移动过去
↓
窗口必须正好露出来
↓
坐标必须正确
```

这就是 RPA 的 **fast path**。

# 3. 文本输入也不要默认 keyboard typing

输入：

```text
hello world
```

最慢的方式：

```text
h
e
l
l
o
...
```

更好的：

```text
ValuePattern.SetValue("hello world")
```

如果 App 正确支持 UIA，你实际上不是：

```text
模拟人在打字
```

而是：

```text
直接设置控件状态
```

这就是为什么 native automation 可以比 Computer Use 快几个数量级。

# 4. 浏览器千万不要走 UIA

如果是：

```text
Chrome
Edge
Chromium
Electron（可暴露调试端口时）
```

直接：

# **CDP**

Chrome DevTools Protocol 官方提供 DOM、Runtime、Input 等能力，可以直接 inspect/manipulate Chromium 页面。([Chrome DevTools][6])

所以：

```text
Chrome
 ↓
UI Automation
 ↓
找 DOM button
```

不要这么干。

直接：

```text
Rust
 ↓ websocket
Chrome DevTools Protocol
 ↓
DOM
```

例如：

```text
DOM.querySelector
DOM.getBoxModel
Runtime.callFunctionOn
Input.dispatchMouseEvent
```

CDP 官方也直接暴露 keyboard/mouse input dispatch。([Chrome DevTools][7])

你的架构因此变成：

```text
Windows Desktop App
       ↓
      UIA

Chrome / Edge
       ↓
      CDP
```

这已经能解决大量企业 RPA 工作。

# 5. 截图：DXGI，不要 GDI BitBlt

视觉 fallback 我会直接上：

# **DXGI Desktop Duplication**

微软的 Desktop Duplication API 可以直接拿到逐帧 desktop update，而且数据是 **DXGI GPU surface**，可以继续利用 GPU 处理。([Microsoft Learn][8])

也就是：

```text
Desktop
   ↓
DXGI Output Duplication
   ↓
ID3D11Texture2D
```

不要：

```text
GetDC
BitBlt
HBITMAP
CPU copy
OpenCV
```

如果你的 OCR 最终也是 GPU inference，这里尤其重要。

理想状态：

```text
D3D11 texture
      │
      ▼
GPU crop / resize
      │
      ▼
OCR tensor
      │
      ▼
GPU inference
```

尽量不要：

```text
GPU
 ↓
CPU RAM
 ↓
resize
 ↓
CPU RAM
 ↓
GPU
```

来回搬。

如果你要**指定窗口**而不是整个 monitor，Windows 现在的 `Windows.Graphics.Capture` 也可以直接针对窗口创建 capture item。([Microsoft Learn][9])

所以我会：

```text
全屏/屏幕变化监控：
DXGI Desktop Duplication

单窗口视觉 fallback：
Windows.Graphics.Capture
```

# 6. OCR：现在不要 PP-OCRv5 了

这里需要更新一下我们刚才聊的东西。

截至 **2026 年 8 月**，PaddleOCR 最新这一代已经是：

# **PP-OCRv6**

它在 2026 年 6 月发布，有：

```text
tiny
small
medium
```

三档。官方当前 OCR pipeline 默认也是 PP-OCRv6_medium。([PaddlePaddle][10])

如果我们的场景是：

> GUI RPA

我不会只跑一个模型。

而是：

```text
                 OCR request
                      │
                      ▼
                PP-OCRv6 tiny
                      │
               confidence OK?
                /            \
              YES             NO
               │               │
               ▼               ▼
             return      PP-OCRv6 medium
```

### 为什么？

绝大多数 GUI 字体：

```text
保存
取消
确定
用户名
订单
Search
Submit
```

都非常规整。

根本没必要每次 medium。

官方 PP-OCRv6 tiny 只有极小规模，而 medium 最大到约 34.5M 参数；PP-OCRv6 本身就是按 tiny/small/medium 设计用于不同算力场景。([PaddlePaddle][11])

所以：

```text
tiny = fast path
medium = accuracy fallback
```

非常适合 RPA。

# 7. OCR runtime：ONNX Runtime

Rust 里我不会带：

```text
Python
PaddlePaddle runtime
```

而是：

```text
PP-OCRv6
    ↓
  ONNX
    ↓
ONNX Runtime
```

Rust 可以直接绑 **ONNX Runtime C API**；官方 C API 支持创建 session 并注册不同 Execution Provider。([ONNX Runtime][12])

然后根据机器选硬件。

如果你明确有 **NVIDIA RTX**，我的性能优先级是：

```text
TensorRT EP
    ↓
CUDA EP
    ↓
CPU
```

ONNX Runtime 官方说明 TensorRT EP 在 NVIDIA GPU 上可以获得比通用 GPU acceleration 更好的推理性能。([ONNX Runtime][13])

如果你想：

> 随便什么 Windows PC 都跑

那现在微软更推荐 Windows 走 **WinML**，它可以根据硬件动态选择 execution provider。([ONNX Runtime][14])

所以可以做：

```rust
enum InferenceBackend {
    NvidiaTensorRt,
    NvidiaCuda,
    WinML,
    Cpu,
}
```

启动时 benchmark 一次。

这个优化可能比换 OCR 模型还明显。

# 9. 再进一步：利用 DXGI dirty rect

这是我尤其建议你做的。

Desktop Duplication API 本来就适合处理 desktop frame updates，并提供 GPU surface。([Microsoft Learn][8])

你的 visual tree 不需要：

```text
每次重新 OCR 整个窗口
```

而是：

```text
Frame N

┌───────────────────┐
│                   │
│     unchanged     │
│                   │
│         ┌────┐    │
│         │NEW │ ← dirty region
│         └────┘    │
└───────────────────┘
```

只 OCR：

```text
dirty region
```

然后更新：

```rust
VisualTree
```

于是可以维护：

```rust
struct VisualElement {
    text: String,
    rect: Rect,
    confidence: f32,
    frame_id: u64,
}
```

变成一个 persistent visual accessibility tree。

这个设计很强。

## 最重要的是执行优先级

最后你的 `click("保存")` 实际应该走：

```text
click("保存")
      │
      ▼
① 已缓存 element？
      │ YES
      ▼
InvokePattern
```

没有：

```text
② UIA selector
      ↓
IUIAutomationElement
      ↓
InvokePattern
```

还没有：

```text
③ Browser?
      ↓
CDP DOM / AX
      ↓
DOM action
```

还没有：

```text
④ 已缓存 OCR visual tree?
      ↓
bbox
      ↓
click
```

还没有：

```text
⑤ DXGI/WGC ROI capture
      ↓
PP-OCRv6 tiny
      ↓
找到？
```

低置信度：

```text
⑥ PP-OCRv6 medium
```

仍然找不到：

```text
⑦ GUI grounding / VLM
```

最后：

```text
⑧ coordinate + SendInput
```

也就是：

```text
        ┌─────────────────────┐
        │  semantic native    │   微秒/毫秒级
        │ UIA / CDP / cache   │
        └─────────┬───────────┘
                  │ fail
                  ▼
        ┌─────────────────────┐
        │  cached visual tree │
        └─────────┬───────────┘
                  │ fail
                  ▼
        ┌─────────────────────┐
        │ PP-OCRv6 tiny       │
        └─────────┬───────────┘
                  │ fail
                  ▼
        ┌─────────────────────┐
        │ PP-OCRv6 medium     │
        └─────────┬───────────┘
                  │ fail
                  ▼
        ┌─────────────────────┐
        │ GUI VLM             │   最慢/最贵
        └─────────────────────┘
```

**这就是我认为 Windows-only 场景下目前最强的设计。**

它不是“Rust RPA + OCR”，而实际上是一个 **Windows-native Agent Runtime**：UIA/CDP 是极速主路径，DXGI + PP-OCRv6 是视觉路径，VLM 只负责真正无法结构化处理的异常情况。

如果你的机器还有 **NVIDIA RTX**，那就更爽：我会把 `DXGI → GPU crop → PP-OCRv6 tiny → TensorRT` 整条视觉路径尽量留在 GPU 上，避免 CPU↔GPU 来回拷贝；这一版才值得认真 benchmark。([Microsoft Learn][8])
